# 导出结果独立核对

仅适用原有严格六项匹配的单来源且税务资料已核实的旧规则时，在导出四份Excel后、刷新正式余额前运行 `scripts/validate_invoice_outputs.py --legacy-six-exact --metadata 本批运行记录/authoring.json --report 本批运行记录/independent_audit.json`。缺少 `--legacy-six-exact` 时入口会拒绝执行。本项目已采用新部门规则，不能使用旧脚本的 PASS 代替已验证的新规则独立审计，即使部门字段本批均非空。脚本只读业务工作簿；仅指定的独立JSON报告可写，失败退出码为1。不得依据脚本退出0替代视觉审阅。

此核验器独立从实际来源和开票单重建六项分组与源行使用，不调用规划helper的求解代码。它检查金额、数量、余额、拆分、红字与删除、未用行保留、税务原文逐字符、EP、公式缓存及输入版本。

核验器默认检查税务完整的严格分支。用户已明确授权“形式发票”或空白红底后补税时，先按本项目已确认规则适配对应税务分支，分别核对文字/空值、仅开票明细单元格的红底以及待补状态；其他财务及溯源检查全部保留。不能为了得到PASS跳过整段税务或金额核对，也不能用严格分支否定用户已经允许的后补结果。

新批次另核对法律主体连续列示：从实际开票单按行读取规范化的公司名称与代码键，离开某主体区块后不得再次出现该键。此检查与六项费用分组独立，不要求同主体所有记录合并成一行。金额规划完成后稳定按主体分块，写回最终计划的target_row，再核对开票公式、税务文本/红底及全部目标行追踪；不能用尚未重排行号的旧计划直接比对。既有核验脚本未检查此排列时，补充只读相邻性检查，不能仅凭旧脚本通过宣称已验证。新规则不追溯否定以前已交付的历史顺序，也不改变只补税等窄请求的范围。

每批另独立重建各来源的顶部使用登记及对账：本批登记额等于该来源新增已用明细之和，各源本批登记之和等于开票总额；历史登记保留，同商品不同批次可区分，同批重试不重复。同源标红版和剩余版登记一致，未使用来源登记0。余额从实际未用行独立求和，标红版的红字不进入余额；已有顶部登记与历史红字不重复累计。核实原始基准及此前已用，再检查“原总额＝剩余＋累计已用”差额为0，不能仅凭G2缓存为0宣称通过。

检查追加登记后的公式确实覆盖全部历史和新位置，不能固定到I:M；canonical控制区不得覆盖I:L数据身份。元数据保留source_original_total、previous_used、current_used、cumulative_used、remaining及差额和各登记单元格。旧核验器若未覆盖这些字段，先扩展相应只读检查，不宣称已有能力；历史复核保留当批原格式，规则更新本身不改写旧文件。

## 多来源与空部门能力边界

现有单源核验器不支持本项目的新部门缺失及匹配规则、多个金额来源、来源优先目标或canonical I:L布局。项目采用新规则后，即使本批数据部门均非空，也不能以旧核验器返回PASS代替新规则审核；应按 [multi_source.md](multi_source.md) 使用已验证支持新规则的规划器和独立审计，逐组检查两个部门字段的非空冲突和来源金额未重复使用。不能忽略L列、把多个来源压成无身份单源，再用旧脚本返回PASS。

多来源元数据至少逐源保留输入哈希、来源编号与优先级、原始文件/工作表/行号、每行原额/用额/余额、每源标红/剩余路径及哈希；行标识不能只有一个没有来源的行号。核对表增加逐源贡献、跨表组余款、来源优先最优性与固定最优值下最少组证明。单源税务兜底检查同样保留。

特别核对：四个必填字段完整且匹配；申领部门和使用中心必须同时非空且逐字一致，来源行才能合组。任一部门字段为空时，该组必须恰好只有一条来源行，不得补填、不得与另一空白行或非空行合并；开票单对应部门字段保留原空白。不得人工指定空白行的部门归属。每个可参与来源行只能属于一个组，组使用额、余额及第一来源优先证明必须一致；单价整除和300元规则按组判断，不能误用到单个来源贡献或来源余额；第二表相同金额记录没有被无依据去重。内部canonical A:H保留原字段、I:L保留来源编号/原始文件/原始行号/优先级，其余额与逐源剩余是同一集合而非新增金额。网站模式的新版快照、索引和 canonical 应保留 `source_outputs` 及来源优先级用于追溯，但只有网站数据库能推进下一批余额；旧本地模式才以验证后的工作副本和索引衔接。

现有单源 `authoring.json` 的 `inputs.source`、四路径和单个row映射只说明旧格式契约。新分支必须显式适配元数据与全部相关业务检查，不能仅把六份输出的其中四份塞进旧参数而称完整核验。

## 元数据约定

`authoring.json` 包含：
- `context`：`product`、元为单位的`price`/`total`、整数`quantity`、三份快照的`inputs.source/template/tax`绝对路径；可选`protected_sha256`记录交付前固定工作副本/索引/原输入哈希。
- `plan`：只读规划helper输出；同目录有`plan.json`时优先读取该文件。
- `paths.invoice/marked/remaining/audit`：四份实际导出文件绝对路径。
- `marked_mapping`、`remaining_mapping`：按目标行逐行排列的对象，含`source_row`、`target_row`、整数分`amount_cents`（非成本行null）、`status`。成本状态为`current_used`/`historic_used`/`available`；非成本行为`header_or_control`。

核对表沿用本项目四页及字段顺序：`核对汇总`的B5:B9为批前可用/本批使用/批后剩余/数量/分组数；`分组明细`A:O为组/申领人/部门/使用部门/成本中心/法律主体/用途/原组金额/已用/数量/余额/源行/开票行/税务源行/类型；`源行追踪`A:H为组/申领人/原行/原金额/已用/未用/标红版行/剩余版行；`异常与文件`包含所有输入路径、输入哈希及四份结果路径。

目前确认的开票单控制格为A1 EP、A2商品、I2单价、J2数量、K2总额，来源控制公式为C2、E2、G2及D2/I2历史额。其他布局、只补税等窄请求、未提供税务、需要用户确认override或新增控制格式时，应先按实际模板适配核验器，保留全部对应业务规则，不为获得PASS删掉检查。

上述来源控制格只是旧布局定位，新增顶部登记后可按实际含义调整C2/G2或余额汇总范围。应保留原始基准与历史登记，并验证新的完整引用及零差额；不能要求旧公式文本或固定I:M范围不变。标红版若改为另列未用余额，审计同步读取该字段并从实际未用行重算，不用全部成本合计代替余额。

## 已交付批次

正式工作余额和索引推进后，使用 `--historical` 重新核对历史批次。此模式只跳过`context.protected_sha256`所指现行工作文件，仍验证`plan.input_sha256`中当批快照及全部业务结果，不能用它绕过正式交付前的版本冲突检查。

验证器通过后，还需核对实际导出文件版式；提交固定余额和索引时应再次检查输入版本未变、输出哈希与核对报告一致，并保存提交记录。异常重试不能重复扣减。
