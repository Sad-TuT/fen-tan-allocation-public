# 费用分摊与开票工作流程

本文件补充完整批次、持续批次和窄范围请求的操作与核对要求。价格、总额、产品、公司资料和文件路径都是每批输入，不能从历史示例写死。

## 1. 模式与输入定位

| 本次请求 | 主要输入 | 执行范围 |
|---|---|---|
| 完整新批次 | 当前来源余额表、模板、产品、单价、精确总额，可选税务表 | 规划、填单、税务、标红、生成余额、核对，默认四份输出 |
| 只补开票明细 | 已确认开票单、税务表，可选已确认修正 | 精确匹配并填开票明细；金额、数量、来源分配保持原样 |
| 只标红已用金额 | 已确认分配及对应来源 | 按实际用额标红与拆分；不重选组、不改变开票金额 |
| 删除红字已用行 | 已标红来源 | 按成本列红字识别并整行删除，另存剩余表 |
| 只核对 | 指定的来源、计划或已交付文件 | 只读审核并反馈；仅在用户要求时生成核对文件 |

先利用用户指定、已确认上下文、表头和模板读取输入含义。若多工作表或多版本无法唯一定位，询问必要的选择；不能凭文件名相似或修改时间猜测。

来源金额列常叫“成本”，目标对应“部门使用金额”；“使用部门”与用户所称“使用中心”是此流程的字段别名，不表示可把不同单元格内容合并。读取真实表头定位列，不能只假设所有来源都固定列号。跳过标题、控制数、表头、空行；若模板或源表有汇总公式，不能作为明细参与分组。

税务表在已确认格式中：F 法律主体编码、G 实际主体名称、H 当前主体类型、J 社会统一信用代码、K 注册地址、L 开户行、M 银行基本户账号。校验表头语义；格式变化时先正确映射，再应用规则。

记录所用文件的绝对路径、工作表、SHA256、记录数、金额合计和本批参数。保留未经修改的输入；输出在独立批次目录另存，不覆盖此前交付。

### 固定目录启动

项目若有 `账目分摊目录配置.json`，用户发出“读取固定输入目录”即按配置中的标准文件路径读取，不再要求重复提供路径。每个新批次使用本次放入的来源布局：

```text
项目根/
  01_输入/
    01_金额来源/
      本批第01来源.xlsx
      本批第02来源.xlsx（可选）
    02_开票模板/开票模板.xlsx
    03_税务主体/税务主体.xlsx
  02_输出/
    日期时间_商品_金额/
      输入快照/
      本批四份结果.xlsx
```

`01_金额来源/` 只放本批明确要使用的余额表；下一批应重新放入上一批核对后的剩余表。用户明确指定多个金额来源时记录其身份、角色和顺序，按 [multi_source.md](multi_source.md) 处理，不能把多个明确来源误作冲突版本。用户指定其他名称时按指示读取；出现真正多版本歧义时询问，不取 mtime 最新项。不把输出历史、旧输入快照、已标红来源或旧网站快照当作新增余额扫描。

启动句应带本批商品、单价和精确总额，例如“使用 $invoice-cost-allocation，读取本项目固定输入目录。商品：本批商品；单价：本批单价元；开票总额：本批总额元；按完整流程执行。”文件放入目录后，由收到的任务指令启动，不自行设置后台监听或定时任务。

读取输入前先确认这是新批次，并只读取本批明确提供或上传的一份或多份余额表。网站每批最多接受10份、每份最多10 MB；多份来源等权一起计算，编号按上传顺序生成，只用于追踪和逐源出表。网站不维护共享余额，也不存在按网站版本自动同步的跨批次余额。不得为了补齐本批金额而自动读取旧快照、旧`当前可用金额.xlsx`、上一批 canonical、历史输出或批次索引；这些文件只用于追溯。若输入目录中的版本、全量/新增含义或承接关系不能唯一确定，先停止并询问。

每批开始时先将实际读取的全部本批余额来源、模板及已提供税务文件复制到该批 `输入快照/`，核对哈希并按接收顺序记录来源编号。全部输出和双核验完成后，由用户确认本批完成。多来源逐源保留标红/剩余结果，同时生成带 I:L 来源追踪的 canonical 用于本批结果、核对和归档，索引记录 `source_outputs` 和来源编号。canonical 和输出剩余表都不是下一批自动入口；下一批由用户重新上传选定的资金表；若继续使用已扣过的资金，必须使用已核验的剩余表。旧输入仍保存在快照中；模板与税务源保持原始数据。

失败、未获授权的税务待确认临时批次、规划测试不推进余额或索引。用户已允许税务后补时，按已确认fallback核验财务及税务待补状态后可以提交，索引保留待补状态。重试先核对既有目录、快照、输出和索引，续同一批，不能重复扣减。历史结果按实际存在文件归档，不伪造缺少的历史核对记录。

## 2. 连续批次与防止重复使用

每一批都从本次明确放入或上传的一份或多份余额表开始。下一批由用户选择并重新上传；如果选择继续使用上一批来源，必须上传已核验的剩余表，并在新批输入快照中重新登记文件名、哈希和来源编号。不得从旧输出、网站历史或索引自动带入。

项目存在 `账目分摊批次索引.json` 时，索引只记归档路径、批次和追溯哈希，不能成为自动余额来源。用户未要求跨项目时不读写其他项目索引。测试输出、无解结果和仍待确认的临时版本不推进正式状态。历史产品、单价、总额是记录，不自动补作新批参数。

- 如果用户明确提供新的全量余额版本，以该版本为本批基准，不再叠加上一批剩余表。
- 如果用户明确提供新增明细，仅在能与既有余额区分、并已确认需要合并时追加；保留每份输入的出处。若无法可靠排除重复，确认后再合并。
- 如果“新输入”是全量余额还是新增明细不明，必须先问。不能把来源原表、已标红副本、剩余表当作三份独立余额相加。
- 若来源仍含红字成本行，按历史已用排除；不把这些行再次加入可用金额。之后删除红字只是剔除记录，不再从已排除的可用总额中扣一次钱。
- 区分原文件总额、历史已用金额、本批前可用金额、本批使用金额、本批后剩余金额。恒等式为：原文件总额＝历史已用＋本批前可用；本批前可用＝本批使用＋本批后剩余。
- 多个版本冲突时综合明确指示、已交付链路、文件内容、记录数、控制数和哈希；不能只使用最新修改时间。哈希用于识别版本，不证明该版本业务上正确。

新批次的默认判断沿用已经确认的业务规则。价格、总额、产品和税务修正仍按本批资料读取，不能沿用旧值来填补真实歧义。

读到canonical来源编号/原始文件/原始行号追踪列时，按 [multi_source.md](multi_source.md) 保留行级身份和L列来源编号。canonical与各源剩余是同一金额集合，不重复相加；旧单来源helper不能忽略这些列运行。

## 3. 分组与精确规划

### 3.1 费用信息匹配

申领人、成本中心、费用承担法律主体、申领用途为必填且须一致；申领部门和使用中心可以缺失，但任一缺失时该来源行只能独立成组。两条记录只有两个部门字段都非空且逐字一致时才能合并；其余字段按原值一致判断，法律主体仅按已确认的名称与代码换序规范化。

法律主体等价要求名称和代码均一致。公司代码只按一个 `L` 加六位数字识别；名称中的其他字母数字片段不视为代码，无法唯一识别时按原文隔离并将税务明细留待人工核实。允许二者顺序及代码配对外围括号 `()`、`（）`、`[]`、`【】` 表达不同。只移除代码外围的配对括号，不移除公司名称内部括号。不能仅凭同码忽略不同名称，也不能用同音字、简称或近似名称强行合并。保留原文用于输出与核查。

缺少信息的记录不自动从同名人员或相邻行补全；申领人、成本中心、法律主体及用途仍需完整。其余必填字段缺失的记录不能用于分摊，仍须保留余额。

申领部门和使用中心（旧表头可能写“使用部门”）必须同时非空且逐字一致，来源行才能与其他行合并。任一字段为空时，该来源行单独成组，不得补填，也不得与另一条空白行或任何非空行合并；开票单对应部门字段保留原空白。不得改写来源的空值及非空原文。跨来源时各源行保持身份且金额不得重复使用。

空白部门行只按自身金额独立参与精确求解，不存在候选部门或人工归属。每条原始可用记录的完整批前金额唯一归属一个组；只允许按已用与未用邻行拆分，禁止拆到多个部门组，也不能把未用部分移出组以规避余额门槛。记录原始身份、归属及金额守恒，不得虚构金额。无法完成合格求解或验证时停止受影响的正式分摊，不把未验证说成无解。

### 3.2 金额约束

设一组可用来源合计为 A，本批使用为 U，单价为 P，数量为 Q，余额为 R：

- U＝P×Q，Q 为正整数；0＜U≤A。
- R＝A－U；R＝0，或者 R≥300 且 R 为整数元。
- 所有 U 的和必须精确等于本批总额 T；T/P 必须为整数。
- 余额门槛按组，不按每个源行、原行剩余或拆分行判断。

多来源时A是该组全部来源之和；各来源用额不必单独是P的倍数，来源各自余额不单独受300元门槛限制。只检查整个合并组的U和R，并逐源保持金额守恒。

采用 Decimal 或整数最小货币单位计算，不用浮点容差把不合规结果视为通过。若 A 含非整数元的小数部分，整数金额的分配会保留该小数；不能通过取整消掉它。组内小数若合计为整数，应按真实合计判断。

本项目多份资金来源等权。精确满足金额、组余额和总量限制后，先最少使用业务分组；如有多个同样少组的方案，按稳定业务分组键确定，确保结果不随文件上传顺序改变。来源编号只用于选定组后的来源记账，不是资金选择目标。开票显示顺序另按第4节的同法律主体连续列示规则安排。用户另行明确资金选择目标时，先确认并单独更新规则。仅要求主体相邻属于显示排序，不改变金额方案或求解目标。

本项目多来源等权共同计算，求解先最少业务分组、再用稳定业务键打破平局，详见 [multi_source.md](multi_source.md)。税务允许后补时不筛税务完整度。部门空白例外、多来源或canonical不能用旧helper的默认求解结果代替。

只有适用原始六项严格匹配规则的普通单来源、完整字段且无来源优先级追踪的其他项目，才使用 skill 根目录的 `scripts/plan_invoice.py`；本项目启用新部门缺失规则后，即便本批数据恰好完整，也不能用旧脚本模拟、审计或据其结果断言无解。新规则必须使用已明确支持并经验证的求解器和独立审计。

以下命令仅供其他项目采用旧规则时参考，本项目新规则禁止运行：

```text
python scripts/plan_invoice.py --legacy-six-exact --source 来源.xlsx --template 开票模板.xlsx --tax 税务主体.xlsx --price 25 --total 25000 --product 示例商品 --out plan.json
```

该命令中的数字和名称是调用示例，必须换成本批输入。可用 `--source-sheet`、`--template-sheet`、`--tax-sheet` 指定工作表；没有税务资料时省略 `--tax`；用户确认的税务修正使用 `--tax-overrides 用户确认修正.json --batch-id 本批编号`。修正文件必须采用第4节的 `entities` 结构，并按当前批次或明确未来授权检查范围。通过工作区依赖加载工具取得 Python 执行文件，不固定某台电脑的运行时路径。以实际 `--help` 核实可用参数。

在旧helper支持的普通单来源范围，且用户未授权税务后补时，已有税务表的新批次先加 `--require-tax-complete`，只在税务代码唯一匹配、名称一致、类型及必要字段可核实的候选组内规划。未选税务异常列入 `tax_exclusions`，在核对记录中保留主体、原因和源行；相关金额不改写、不删除。该参数不放宽六项、整除、余额或精确总额规则。用户已允许后补、已确认分配、只补税或指定必须使用某组时，不为避开税务异常自动换组。

若上述筛选后无法精确凑齐，不加 `--require-tax-complete` 再作只读金额规划以判定原因：金额本身有解而所选税务异常时，说明具体需确认的资料并保存待补计划；整体金额也无解时才报告金额约束无解。筛选失败不能直接证明全部资金无解，也不能据此擅改总额。

helper 只读输入，写出包含分配、目标行、源行拆分、税务问题和输入哈希的 JSON 计划，不负责 Excel authoring。计划警告需区分影响本批的阻断异常与未用记录的说明。无法精确凑齐时说明制约原因；可给出可行金额供用户选择，但不能擅改总额、单价或余额规则。

## 4. 填写开票单与税务信息

保留模板原有架构、标题、EP 单号、样式与无关内容。按选组输出四项必填信息；可合并组的申领部门和使用中心填写逐字一致的原值，空白独立组的对应部门字段保留空白；部门使用金额填本次 U，单价填 P，数量填 Q，总计金额与部门使用金额相等。模板行数不足时按同类明细行扩展并正确调整汇总；行数充足时不做无关改版。

开票单将同一费用承担法律主体的记录相邻放置。沿用法律主体名称与代码的规范化键，先按主体首次出现顺序分块，再保持各块内原分组顺序。此排列只影响显示，不改变已选金额、来源记账或六项费用分组；同一主体但其他费用信息不同仍独立成行。先完成金额规划，再安排最终开票行号，整行携带六项信息、金额、数量、开票明细和待补红底，按新行号填写公式并更新计划及核对表的目标行。来源标红版、剩余版和canonical继续保留原来源顺序。仅补税等窄请求保留既有行序，除非请求范围也包含重排；仅记录新规则不改写历史Excel。

只补税时使用已经确认的开票单，不重新分摊。G 开票明细的规则如下：

1. 从 F 法律主体提取唯一 `L` 加六位数字的公司代码，精确匹配税务表 F 法律主体编码；无法唯一识别时不按名称相似度猜测。
2. 要求唯一命中；再将来源公司名称与税务表 G 实际主体名称核对。不得模糊匹配替代代码匹配。
3. 根据税务表 H 当前主体类型决定填入格式。

| H 当前主体类型 | 开票单 G 内容 |
|---|---|
| 小规模纳税人 | 仅 J 社会统一信用代码 |
| 一般纳税人-简易征收 | 仅 J 社会统一信用代码 |
| 一般纳税人-一般征收 | G、J、K、L、M、空行、专票，共七行 |

一般征收七行内容按以下顺序拼接，原文字段不加标签、不改写：

```text
实际主体名称
社会统一信用代码
注册地址
开户行
银行基本户账号

专票
```

统一信用代码、基本户账号按文本保留；不能先转数字再转回文本，否则可能丢前导零或长账号精度。检查源单元格类型与实际文本；若原文件已经用不可靠长数值存储账号，不能推测缺失位。

以下问题要对具体主体提示并等待确认后才修改相关税务内容：代码缺失或不唯一、重复匹配、名称不符、类型空白或超出三种明确分支、所需字段空白、地址/开户行疑似串列、账号精度异常。其他能独立完成的分摊和文件核对继续执行。没有税务表时 G 留空并标明待补，不能假造信息。

用户确认修正时，保留原值、确认后的值、涉及主体、确认依据与本批范围，通过 `--tax-overrides 用户确认修正.json --batch-id 本批编号 --batch-created-at 本批带时区时间` 传入；除非明确授权，不改源税务表。某公司曾确认的文字修正不能自动固化为所有公司或以后批次的修正规则。

用户明确允许“英文主体查不到资料填形式发票，其他不确定明细空白红底”时，按项目业务规则与确认补充资料执行：只把开票明细单元格设红底，不猜主体类型，也不排除其可合法使用的金额。保留待补原因；不能将此授权扩大为修改税号或放宽费用分组。已确认且适用同一税源的修正无需重复询问。

override JSON 以精确公司代码为键，并且必须声明且只声明一种作用范围。例如本批专用为 `{"entities":{"L000001":{"confirmed_by_user":true,"reason":"本批用户确认的原文字段更正","address":"确认后的注册地址","bank":"确认后的开户行","scope":{"batch_ids":["实际批次编号"]}}}}`；用户明确授权未来批次时，须写 `applies_to_all_future_batches:true` 和带时区的 `effective_from_utc`，不能再同时写 `batch_ids`，应用时与本批创建时间比较，过去批次不得套入。仅传入实际确认的字段；示例代码和文字不是有效业务数据。脚本输出中的金额为整数分，实际填写时按100分＝1元转换。

## 5. 按实际使用金额标红

为每个选用组先按来源编号、再按原来源行号递增记账，保留来源编号、文件、工作表与原行号的追踪。这个先后只用于准确归档各来源的用额和剩余，不代表优先选择该来源：

1. 原行全部使用：保留金额数值，将成本单元格改为红色字体。
2. 原行部分使用：邻行拆为已用行与未用行。两行保留一致的六项信息及其他业务内容；已用行成本＝本行实际使用额，红字；未用行成本＝本行余额，正常颜色。
3. 原行未用：保持金额，不新增已用标记。

拆分前后该记录金额总和不变；完整组总额也不变。拆分出的单行余额可以小于300，只要完整组余额为0或至少300。不要为了让单行余额达到300而丢钱或改变已确认分配。

保留原格式和原有注释。若筛选/隐藏导致本次已用行无法查看，可为可审阅输出调整显示状态并保留筛选功能；不把隐藏行当作不存在，也不能只分配当前可见行。已有历史红字保留历史身份，核对时只把本批新增红字计入本批用额。

## 6. 删除已用行，生成下批来源

从标红副本读取成本列红色字体对应的已用行，整行删除并另存“剩余来源表”。筛选依据是金额的已用标记，不能按姓名、部门或整组删除。保留所有未用拆分余额和同组其他未用行。

如果只收到已标红文件执行删除请求，先识别实际红色成本行、计算数量和金额，再删除。若红色含义或格式识别有歧义，先确认；不要凭姓名猜测。

更新受影响的行引用、汇总与筛选范围。确保输出无被遗漏的红字成本行、无空白占位行冒充剩余明细，且剩余明细、汇总公式与下一批规划读取范围一致。

### 顶部逐批使用登记与对账

每批在各来源金额表的输出副本顶部，沿用既有登记格式增加“本批商品＋从本表实际使用的金额”，记录来源编号和批次标识以便追踪。金额取该来源原行的本批实际使用额之和；同一商品由多个来源承担时分别登记各自贡献，所有来源的本批登记之和等于本批开票总额。参与本批但未使用的来源登记0。原始上传文件保持不改写。

历史商品及金额完整保留；同商品不同批次分别登记并标明批次，不能用新金额覆盖历史额。同一批次重试或只重排开票单、补税时不新增支出、不重复累计。使用下一个空白控制位置；位置不足时扩展顶部控制区及其引用，不覆盖原始总额、历史登记、业务表头或canonical来源追踪字段，也不能假定只允许登记到M列。

每个来源独立核对以下三式，金额用整数分或精确十进制：

- 累计已用金额＝此前各批已用合计＋本批从该来源实际使用额。
- 本批前可用＝本批使用额＋本批后剩余。
- 原总额＝本批后剩余＋累计已用金额，核对差额必须为0。

“原总额”沿用该来源已确认的原始基准；输入已是上一批剩余表时，保留其原总额及完整历史，不把本批前余额改称原总额后再叠加旧支出。累计已用只计各批各源一次；已有顶部历史登记及对应历史红字属于同笔支出，不能分别累加。历史数据不全时先从已验证快照、索引及核对记录恢复，不伪造历史额或调整原总额来凑出零差额。

首次启用或历史顶部登记不全时，以“来源编号＋批次标识”对齐现有登记与已验证支出记录；已扣除但尚未登记的历史支出在新输出中作期初承接或历史补登，只计一次。不能仅把现有顶部列的合计当全部历史，也不能依据差额猜测某批使用额。本次只更新规则时不回写旧文件。

各源标红版和剩余版顶部登记一致。剩余版的余额可由全部剩余成本明细独立求和；标红版还保留已用红字，余额须仅对未用明细求和。若标红版原E2仍为全部成本合计，另设清晰的未用余额控制值并调整对账引用，不能用“全部成本＋本批使用额”重复计算。余额、登记额与原始基准分别从明细、逐源分配及历史资料核实，不用倒算余额来证明同一恒等式。

更新剩余合计、累计已用、差额及本批登记的实际引用范围，保留有效原公式；新增控制列超出旧I:M范围时同步扩展，不漏掉新批次。不能把计算引擎不支持函数产生的错误文本当正确结果交付。将逐源原总额、此前已用、本批已用、累计已用、剩余及差额纳入核对记录与来源衔接元数据。

## 7. 默认文件与核对记录

若项目业务规则配置了 `output_archive`，每个正式批次单独归档，按目录配置的 `batch_subfolder_pattern` 在目录末尾附上累计已分摊商品。累计列表必须继承本批实际使用余额的上一批次链，再按批次编号追加本批商品；保存商品原文和对应批次编号，不按商品名去重，不通过扫描文件夹或全项目历史推定。正式成功的财务批次（包括已授权税务后补的已入账批次）纳入列表；试算、失败、同批重试、补税或重新排序不新增条目。括号清单包含本批，当前目录仍只包含本批结果及其快照、运行记录。Windows目录分隔展示使用全角 `／`，不能用ASCII `/` 或 `\` 造成嵌套目录；商品名中其他非法路径字符只在目录展示时转义，原文保留。新批核对记录及索引保存累计列表、余额前序批次和实际目录路径。现有历史目录不自动重命名，也不因此修改余额或已交付索引。路径长度不满足宿主限制时先缩短非必需前缀；仍无法完整展示清单时说明并确认替代展示，不静默遗漏商品。

完整批次默认交付以下四份文件；名称包含产品、本批金额或批次标识，避免与历史混淆：

1. 完整开票单：本批各组、金额、单价、数量、总计金额和可核实税务明细；税务缺失时明确待补。
2. 已标红来源副本：来源明细完整保留，部分金额邻行拆分，历史已用与本批已用可追溯。
3. 剩余来源表：全部已用红字行已删除，金额为本批结果中的未用余额。它只作为本批归档；下一批使用时必须由用户重新上传并重新核对。
4. 分摊核对记录.xlsx：记录本批输入、分配、源行使用与拆分、税务匹配、核对结果和输出清单。

上述为单来源默认；N来源按每源分别输出标红版和剩余版，共2N+2份用户结果。两来源为六份，最多10份来源。网站结果使用 `YYYYMMDD_商品_批次短ID_来源编号_剩余.xlsx` 等命名。canonical A:H原字段、I来源编号、J原始文件、K原始行号、L来源编号追踪值，按 [multi_source.md](multi_source.md) 保留。canonical 只用于本批映射与审核，不自动衔接下一批。

核对记录按实际数据量用紧凑工作表呈现，至少包含：

- 批次标识、产品、单价、精确目标金额/数量；输入绝对路径、工作表、SHA256、输出文件及上下批次关系。
- 原文件总额、历史已用、本批前可用、本批使用、本批后剩余；记录数与删除/拆分数量。
- 每组选用的六项信息、原可用合计、使用金额、数量、余额、模板目标行。
- 原文件源行号、原金额、本批已用、本批未用、拆分后对应行与红字状态；行号变化后仍可追溯。
- 税务主体代码、匹配源行、类型、所需字段是否完整、确认修正及待确认异常。
- 多来源的各源用额/余额、原行身份和来源编号、跨表组贡献、最少业务分组证明、canonical与各源剩余的逐行映射。

核对记录是审核结果，不应作为开票单公式必需的中间计算表。不要把计划 JSON、脚本、预览图片默认增加为用户交付物。

## 8. 导出前与导出后核对

Excel authoring、公式重算、导出和视觉检查遵循可用的 **Spreadsheets** skill；本技能的业务规则补充其通用能力，不替代工具规范。

检查以下实际结果，不只检查公式文本或脚本成功退出：

- 所选每组必填字段匹配、两个部门分别无非空冲突，来源不超用，旧红字未再分配；缺失信息没有被擅自补造。
- 申领部门和使用中心都必须非空且逐字一致，来源行才能合组；任一字段为空时检查组内只有一条来源行，开票单保留空白原值；逐行检查金额归属不重复。
- 每行 U/P＝Q 为整数，金额合计＝T，数量合计＝T/P；部门使用金额＝总计金额。
- 每组选用后的 R＝0 或大于等于300的整数元；小数无四舍五入消失。
- 本批新增红字金额合计＝本批使用；拆分前后金额守恒。
- 删除行与所有已用红字成本行集合相符，剩余记录不含已用金额；保留所有未用余额。
- 原总额＝历史已用＋本批使用＋本批后剩余；四份结果之间同组与整体金额一致。
- 各源顶部均有本批商品及本源实际用额，历史记录未覆盖且同批未重复登记；累计已用完整，逐源“原总额＝剩余＋累计已用”差额为0，标红版余额排除红字；新增登记均纳入实际公式引用。
- 多来源还需逐源守恒及合并组余额核对，证明选中组数达到全局最小值；canonical I:L与索引 source_outputs 及来源编号一致。不能把单源验证器用于忽略这些信息后的假验证。
- 税务代码唯一精确匹配、名称一致、类型分支正确；一般征收含七行及空行、专票，另两类仅信用代码。
- 信用代码和账号完整文本保留，税务异常与用户确认修正有记录。
- 模板 EP 原样保留；无关数据、样式和对象未被改变；汇总/筛选范围与实际行数一致。
- 本批新开票单中，同一规范化法律主体只占一个连续区块；排序前后各组金额、数量、税务明细及待补红底对应一致，公式引用和核对追踪使用最终行号，不符合费用匹配规则的记录未因同主体被合并。
- 重算后无新增公式错误；长部门名称、一般征收多行明细、金额和数量清晰可读，无截断。

交付简述本批金额/数量、剩余总额，并明确写出下一批要由用户重新上传的逐源剩余表；指出仍需确认的具体主体或字段。仅在请求真正需要用户判断时停下等待，不在每个机械步骤重复询问是否继续。

### 8.1 项目要求的异常询问与双agent核验

项目 `quality_control` 要求双agent时，每次完整制表及修改交付表格均执行本节。只读解释问题不触发重制或扣减；只补税、重排等窄修改不重新分摊，两位复核者仍核对财务数据与原已确认版本一致。

遇到新的来源版本不明、资料缺失或冲突、金额无解、未经授权的税务处理、公式差异或复核不一致，先向用户说明具体文件、记录或差额并询问，暂停依赖该问题的步骤；可继续只读定位与复算。已明确确认的部门空白例外及税务后补安排继续沿用并列明，不视为新未决问题。普通工具故障按既有规则处理；无法恢复或影响核验覆盖时如实说明。不能擅自修改业务数值、税务类型或既定规则让核验通过。

导出后冻结实际输入快照及最终结果清单、哈希，同时启动两名不同的独立复核 agent。给两人相同的原始输入、本批参数、用户确认规则和待交付文件；不提供预设财务答案、通过结论、制表者计划或另一复核报告。两人都须自行从原始来源和最终 Excel 重算金额、数量、分组、合并组余款、逐源使用及余额、拆分与删除行、顶部历史登记和对账恒等式；按本次范围核对最少业务分组目标、税务修正作用范围、全部输入/输出哈希、主体排列、公式结果和溯源。网站中的“确认本批完成”只归档本批，不更新共享余额，也不能代替两名独立复核。可补充分工检查，但不得以“一人只看金额、一人只看格式”替代两人对核心计算的独立核验，也不能只重复运行制表者同一个脚本就声称独立验证。

各自保存报告，注明复核agent身份、核验范围、输入和最终输出哈希、独立计算结果、异常/未验证项及通过状态。两份报告作为本批过程记录保存，不增加默认六份用户Excel的数量。现有分摊核对记录在最终冻结前登记复核者身份、核验范围及报告位置；最终双审结论和哈希写入Excel以外的运行记录及交付说明，终审后不回写Excel而改变已审核版本。若需回写任何摘要，先完成回写，再对最终版本取得两份终审报告，不能形成不断回写和重审的循环。主agent汇总两份结论，并核对审查后文件未变。任何失败、结论冲突、覆盖缺失、复核工具不可用或新未决问题均不得以通过交付或刷新余额；向用户说明并询问，不能悄悄降为单人核验。修正后对最终文件重新取得两份有效核验，不能用旧哈希报告放行修改后的版本。普通复核不修改业务文件或余额。
